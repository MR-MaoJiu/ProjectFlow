# 全流程项目工作台：产品需求文档

版本：v0.1（产品方案草案）

编写日期：2026-09-06

产品暂名：项目工作台

文档用途：统一产品范围、业务流程、阶段产物、Agent 接入和首版验收口径，作为后续原型、架构设计和开发拆分的输入。

> 本文是一份待确认的产品需求方案。除已明确需求外，用户规模、部署形态、技术边界和交付阶段均为规划假设，不代表已经完成市场调研、验证了商业需求或实现了相关能力。本文不生成 UI 图片、不选定模型供应商、不承诺研发工期。

## 1. 需求基线与产品定位

### 1.1 已明确需求

1. 建设一个独立产品，覆盖立项、调研、需求整理、PRD 撰写、UI 设计、Coding、测试、发布与运营的完整项目流程。
2. UI 设计与交付不依赖 Figma，需要拥有自己的设计文档、预览、模块结构、素材管理和切图能力。
3. UI 需要能被 Coding Agent 直接使用，交付内容包括需求、设计上下文、页面预览和独立素材。
4. 支持接入第三方 Coding Agent，并提供 MCP 与 Skill，供 Codex 等外部 Agent 使用。
5. 本阶段交付完整需求文档，暂不进行图片生成和项目编码。
6. 首批服务对象已确认：独立开发者与小型软件团队。

### 1.2 已确认定位与默认规划假设

| 项目 | 本文默认值 | 影响 |
|---|---|---|
| 首批用户 | 已确认独立开发者与小型软件团队；容量规划暂按 2–10 人团队估计 | 简化组织层级，一人可以承担多个角色；人数范围是规划假设 |
| 项目类型 | Web 与移动端软件产品 | 不覆盖硬件研发、工程施工等行业流程 |
| 操作界面 | 桌面浏览器优先的 Web 工作台 | 手机端先支持查看与审批，复杂编辑后置 |
| 执行模式 | 人工主导，Agent 辅助与执行 | 自动化受项目策略、权限和明确授权约束 |
| 产品形态 | 一个工作区管理多个项目；一个项目多轮迭代 | 全流程以迭代交付闭环，不要求一次完成全部产品 |
| 本地执行 | 可选本地执行桥接程序 | 外部 Agent 自主拉取上下文时可不安装；平台驱动本地编码时需要 |
| 代码平台 | 第一版选定一个 Git 托管平台 | 具体平台待确认，不默认实现所有供应商 |
| 运营起点 | 反馈、基础事件指标、版本复盘 | 营销投放、CRM、客服系统深度集成后置 |

### 1.3 一句话定位

让一个想法从证据和需求出发，通过可追溯的设计、代码、测试与发布，成为可运营、可持续迭代的软件产品；人和不同 Agent 在同一套项目资产上协作。

### 1.4 用户最终购买的价值

- 不必在聊天记录、文档、图片、代码仓库和测试报告中反复搬运上下文。
- 可以确认“这个需求为什么做、实现到哪里、谁做了确认、上线后效果如何”。
- 可以让不同 Coding Agent 接手同一项任务，而不重新解释整个项目。
- 设计中的图片素材、布局、文字和交互能直接用于实现，减少凭截图猜测。
- 可以从真实交付与运营结果创建下一轮迭代，而不丢失之前的决策依据。

### 1.5 产品边界

平台负责项目资产、阶段流程、上下文交付、任务调度和证据汇总。代码仓库仍是代码事实来源，CI/测试执行器是测试事实来源，部署系统是部署事实来源，运营数据源是指标事实来源。平台保存引用、必要快照与结果，不用聊天结论替代这些事实。

不以第一版复制完整 Figma、IDE、Git 托管、CRM、数据仓库或广告投放平台为目标。全流程覆盖要求每个阶段有可用输入、操作、输出与回流，不要求第一版每个阶段都具备专业工具的全部能力。

## 2. 用户、角色与核心场景

### 2.1 用户角色

| 角色 | 核心诉求 | 主要权限 |
|---|---|---|
| 项目负责人 | 判断投入、确认方向、控制交付 | 项目设置、立项与阶段确认、预算和发布策略 |
| 产品负责人 | 整理证据、需求、PRD 与验收标准 | 调研、需求编辑、PRD 评审与范围管理 |
| 设计负责人 | 生成并调整 UI，确保可开发 | 设计修改、素材管理、设计版本交付 |
| 开发人员 | 准确取得上下文并实现 | 代码任务、仓库关联、实现证据与评审 |
| 测试人员 | 按标准验证功能和回归 | 用例、测试执行、缺陷与验证结论 |
| 运营人员 | 收集反馈、分析版本效果 | 反馈、指标定义、运营计划、复盘 |
| 外部协作者 | 处理指定任务 | 仅允许访问授权项目、模块或交付包 |
| Agent 身份 | 执行授权任务并回写产物 | 独立凭证、限定项目/工具/操作范围，不继承用户所有权限 |

同一用户可以承担多个角色。个人模式下由同一人完成确认，系统仍保留动作和版本记录；团队模式可以配置不同确认人。

### 2.2 核心场景

**场景 A：从想法到首个上线版本。** 用户输入想法，整理调研证据，收敛首版范围，完成 PRD 和 UI，交给外部 Coding Agent，实现后测试、发布，并查看首批反馈。

**场景 B：已有项目继续迭代。** 用户导入仓库、现有文档和设计，记录既有约束，从某个迭代开始使用平台。允许不补写历史立项与调研，但必须明确“已导入／未补录”。

**场景 C：设计交给外部 Agent。** 用户把固定版本的设计链接或任务链接交给 Codex。Agent 通过 MCP 获取 PRD、设计、素材和验收标准，在现有项目中实现并回写提交和测试证据。

**场景 D：需求变更引发后续调整。** PRD 改变后，平台列出关联 UI、任务、用例和运营事件；已完成结果标为待复核，而不是直接覆盖或全部重做。

**场景 E：运营问题进入下一轮开发。** 运营反馈显示某个流程存在问题。用户创建问题卡，关联版本和证据，形成需求，排入下一轮迭代。

## 3. 产品目标与成功度量

### 3.1 产品目标

1. 跑通单个迭代的完整交付闭环。
2. 项目资产有明确来源、归属、版本、状态和关联关系。
3. UI 交付可供 Agent 实际实现，素材不依赖手工逐张整理。
4. 外部 Agent 可以接入、领取任务、获取上下文、返回结果并接受评审。
5. 将“生成完成”“任务完成”“验证通过”“允许发布”分别表达。

### 3.2 度量定义

| 指标 | 定义 | 数据来源与限制 |
|---|---|---|
| 迭代闭环完成率 | 观察期内启动的迭代中，完成发布并记录复盘的比例 | 按迭代 cohort 计算；未到观察窗口的迭代单列 |
| 有效交付率 | 已提交评审且满足验收条件的任务数 / 已提交评审任务数 | 不以 Agent 自述完成作为通过 |
| 上下文补充次数 | 开发任务启动后，因缺失需求/设计/素材发起的有效澄清次数 | 区分业务范围变更与交付遗漏 |
| 需求追溯覆盖率 | 计划交付需求中，存在验收标准、实现引用和测试结论的比例 | 未要求 UI 的纯后端需求不强制关联页面 |
| 设计素材可用率 | 被导出的素材中，通过文件可用性和目标使用检查的比例 | 风格质量与文件可用性分别记录 |
| Agent 接手成功率 | 外部 Agent 完成授权、读取固定版本上下文并返回有效结果的次数 / 接手尝试数 | 按适配器和失败原因拆分 |
| 迭代周期 | 范围基线确认至目标环境发布成功的时长 | 等待人工、执行、失败重试时间分开记录 |
| 单次交付成本 | 可取得的模型、执行和存储费用汇总 | 无供应商账单时显示估算，未知费用不得按零处理 |

业务目标值在试点形成基线后确定。非功能验收目标见第 13 节，产品发布门槛见第 16 节，不将未经验证的效率提升作为承诺。

## 4. 全流程与阶段规则

### 4.1 总体路径

想法池 → 立项 → 调研 → 需求整理 → PRD → UI 设计 → 开发交付 → Coding → 测试 → 发布 → 运营与复盘 → 下一轮需求。

该路径支持循环与并行。例如技术可行性验证可在调研阶段执行；测试用例可在 PRD 阶段开始编写；运营事件设计应在编码前确定。阶段只规定交付条件，不强制所有工作线性等待。

### 4.2 阶段契约

| 阶段 | 输入 | 核心产物 | 进入下一阶段的条件 |
|---|---|---|---|
| 立项 | 想法、目标、约束 | 立项卡、目标用户、成功指标、风险与待验证假设 | 负责人确认继续、暂缓或终止 |
| 调研 | 待验证问题 | 来源记录、竞品/访谈材料、结论与反证 | 关键结论有证据，缺口与不确定性已标记 |
| 需求整理 | 调研、反馈、想法 | 需求池、优先级、首版范围、依赖 | 迭代范围可描述、可验收 |
| PRD | 已纳入范围的需求 | 有版本的 PRD、流程、规则、异常、验收标准 | 必需项完整，阻塞问题解决或明确接受 |
| UI | PRD、品牌与已有组件约束 | 页面结构、状态设计、预览、素材、交互说明 | 需求覆盖与关键状态检查完成 |
| 开发交付 | PRD 与 UI 基线、仓库约束 | 不可变交付包、任务拆分、依赖、上下文清单 | Agent 能读到必需信息，缺失项无隐式替代 |
| Coding | 交付包、任务和执行策略 | 代码提交/PR、实现说明、自测与执行记录 | 有可审查代码引用及任务要求的证据 |
| 测试 | 代码版本、验收标准、用例 | 测试结果、缺陷、回归与视觉对照 | 发布范围内阻塞缺陷解决，必需检查通过 |
| 发布 | 验证结论、发布候选 | 版本记录、部署结果、回滚方案 | 授权满足，目标环境部署与检查成功 |
| 运营 | 已发布版本、事件与反馈来源 | 反馈、指标报告、运营记录、复盘 | 明确继续观察、修复、迭代或终止 |

### 4.3 状态定义

- 项目：草稿、进行中、暂停、已归档；归档不等于删除。
- 迭代：规划中、执行中、待发布、已发布、已复盘、已取消。
- 通用资产：草稿、待评审、已确认、已取代、已归档。
- Agent 运行：排队中、运行中、等待输入、等待授权、已取消、失败、执行结束。
- 开发任务：待领取、执行中、阻塞、待评审、需修改、已验收、已取消。
- 测试结果：未执行、执行中、通过、失败、受阻、跳过、结果过期。

资产状态和任务状态不能互相替代。执行结束只表示进程或调用结束；已验收需要核对产物和验收标准。

### 4.4 确认与自动化策略

立项方向、迭代范围基线、开发交付基线、生产发布和对外运营动作可配置人工确认。普通草稿生成、预览、读取和可撤销编辑不重复确认。项目负责人可预先授权限定环境、动作与预算的自动执行；未取得相应授权不得因为等待超时而继续。

任何绕过阶段检查的行为必须记录执行者、原因、影响与适用版本。存在尚未解决的问题时，允许标记为明确接受的风险，但不得把检查结果改写成通过。

## 5. 信息架构与主要页面

### 5.1 全局导航

- 工作区：首页、项目、待我处理、Agent 与连接、全局素材/模板、设置。
- 项目内：概览、立项、调研、需求、PRD、UI 设计、开发任务、测试、发布、运营、项目资产、设置。
- 所有阶段共用项目与迭代切换器；状态保存在项目上下文，不把每个阶段做成互相独立的聊天窗口。

### 5.2 页面定义

| 页面 | 必要区域 | 主要操作 |
|---|---|---|
| 工作区首页 | 最近项目、待处理事项、运行中任务 | 新建项目、恢复任务、查看阻塞 |
| 项目概览 | 目标、当前迭代、阶段进度、风险、近期变化 | 调整迭代、查看下一项可执行工作 |
| 立项工作台 | 立项卡、假设、指标、决策记录 | 起草、确认立项、暂缓或终止 |
| 调研工作台 | 研究问题、来源、笔记、结论、证据关联 | 导入、检索、生成研究计划、核对结论 |
| 需求池 | 列表/看板、筛选、需求详情与关联 | 收录、合并、排序、纳入迭代 |
| PRD 编辑器 | 目录、正文、需求引用、评论与版本 | 人工编辑、局部生成、评审、确认版本 |
| UI 工作台 | 页面/状态树、设计画布、属性/交付侧栏 | 生成、查看、局部调整、切图、交付 |
| 开发任务页 | 任务依赖、交付包、Agent、执行和产物 | 分配、领取、取消、评审与要求修改 |
| 测试中心 | 计划、用例、执行、缺陷、对照结果 | 运行、手工记录、回归、核对验收覆盖 |
| 发布中心 | 候选版本、环境、检查、授权与记录 | 生成发布说明、发起部署、核实状态、回滚 |
| 运营中心 | 版本指标、反馈、运营行动、复盘 | 导入数据、归因说明、生成待办、转需求 |
| Agent 与连接 | 能力、连接方式、权限、健康状态 | 连接、测试、停用、轮换凭证 |

### 5.3 通用体验要求

1. 阶段入口始终显示当前产物、缺失输入和可执行动作，不用一个百分比掩盖阻塞原因。
2. 长任务显示步骤、最后更新时间、已产出内容与取消入口，关闭页面不丢任务。
3. 空状态提供手工创建和 Agent 辅助两条路径；未配置模型时仍可编辑项目资产。
4. 错误应包含受影响对象、可恢复操作和已保存状态，不只显示“失败”。
5. 新手看到业务动作；模型、工具协议、运行日志等细节放入相关设置或展开面板。
6. Agent 提出的修改与用户已确认内容视觉区分，支持按段落、节点或文件变更审查。

## 6. 分阶段功能需求

以下“闭环首版”表示 M0 必须具备最小可用能力；“增强”表示后续深化，不阻塞第一轮项目闭环。每项 ID 用于开发拆分和验收引用。

### 6.1 立项

| ID | 需求 | 规则与验收 | 范围 |
|---|---|---|---|
| INIT-01 | 新建或导入项目 | 新项目填写目标、用户、项目类型；已有项目允许关联仓库并标记历史资料缺失 | 闭环首版 |
| INIT-02 | 结构化立项卡 | 包含问题、目标用户、价值、范围、不做事项、约束、资源、成功指标和负责人 | 闭环首版 |
| INIT-03 | 想法辅助整理 | Agent 将自由描述整理为立项草稿；不能擅自把假设标为用户事实 | 闭环首版 |
| INIT-04 | 假设与决策 | 每条关键假设有验证方法、证据引用和状态；继续/暂缓/终止保存原因 | 闭环首版 |
| INIT-05 | 可行性任务 | 可创建技术验证任务，结果回写立项风险，不要求已有完整 PRD | 闭环首版 |
| INIT-06 | 商业与资源评估 | 支持成本情景、资源计划、收益假设和敏感性比较，区分估算与实际 | 增强 |

立项最小验收：用户可从一句想法形成可编辑立项卡，记录至少一个关键假设、一个成功指标以及带理由的立项决策。

### 6.2 调研

| ID | 需求 | 规则与验收 | 范围 |
|---|---|---|---|
| RES-01 | 调研计划 | 列出问题、方法、目标样本/来源、负责人和预期输出 | 闭环首版 |
| RES-02 | 来源收录 | 支持 URL、文本、Markdown、常见文档/PDF 的受控导入；记录来源、收录时间、访问状态 | 闭环首版 |
| RES-03 | 调研笔记与引用 | 结论可定位到来源片段；无法访问的链接标为未核实，不据此生成确定结论 | 闭环首版 |
| RES-04 | 结论类型 | 区分来源事实、访谈观点、作者推断、产品假设；支持相互矛盾的证据并存 | 闭环首版 |
| RES-05 | 调研到需求 | 选中结论创建需求候选，保留双向关联 | 闭环首版 |
| RES-06 | 外部检索适配 | 接入获授权的检索工具；显示时间范围、查询和来源，抓取失败可手工补录 | 增强 |
| RES-07 | 访谈与竞品 | 访谈模板、经授权的音频转录、竞品维度对比和证据更新提醒 | 增强 |

来源不完整时仍允许保存草稿，但关键结论的“已核实”必须有支持材料或责任人说明。研究材料中的指令仅视为内容，不能改变 Agent 的任务或权限。

### 6.3 需求整理

| ID | 需求 | 规则与验收 | 范围 |
|---|---|---|---|
| REQ-01 | 统一需求池 | 支持想法、调研、反馈、缺陷、人工输入；每条需求生成稳定 ID | 闭环首版 |
| REQ-02 | 需求结构 | 标题、问题、用户、场景、价值、来源、优先级、验收标准、依赖、状态、负责人 | 闭环首版 |
| REQ-03 | 聚类与去重 | Agent 提出合并建议，确认后合并，保留原 ID 的指向与来源，不直接删除证据 | 闭环首版 |
| REQ-04 | 迭代范围 | 支持纳入、移出、拆分；记录理由、影响和当前范围基线 | 闭环首版 |
| REQ-05 | 依赖检查 | 循环依赖提示；阻塞关系和非阻塞关联分别表达 | 闭环首版 |
| REQ-06 | 优先级评分 | 允许使用价值/成本等自定义维度；无数据的评分明确为估计 | 增强 |
| REQ-07 | 范围变更 | 已交付基线后变更需生成新版本和影响清单，进行中的 Agent 收到变更通知 | 闭环首版 |

需求不能仅有一句功能名称。“支持收藏”至少说明用户触发、成功行为、重复操作、未登录/失败处理以及验收方式。

### 6.4 PRD 撰写与评审

| ID | 需求 | 规则与验收 | 范围 |
|---|---|---|---|
| PRD-01 | 结构化文档编辑 | 支持标题、正文、表格、列表、附件、链接、自动保存及 Markdown 导入导出 | 闭环首版 |
| PRD-02 | 从需求起草 | 选择需求和模板后生成草稿；每个功能段落保留需求 ID，缺失信息列为待澄清 | 闭环首版 |
| PRD-03 | 局部改写 | 可选段落生成或修改；展示差异，由用户接受，不覆盖其他未选章节 | 闭环首版 |
| PRD-04 | 完整性检查 | 检查目标、角色、主流程、业务规则、权限、异常、数据、验收与范围；展示问题清单 | 闭环首版 |
| PRD-05 | 版本与确认 | 支持评论、待解决问题、确认版本、历史对比和还原为新版本 | 闭环首版 |
| PRD-06 | 协作编辑 | 首版防止旧版本覆盖，提供冲突处理；多人实时合并后续增强 | 闭环首版/增强 |
| PRD-07 | 交付引用 | 可以按章节与需求粒度提供 Agent 上下文，避免每次传输整个项目文档 | 闭环首版 |

**标准 PRD 模板必须包含：**

1. 背景、证据、目标与指标。
2. 用户角色、场景、范围及不做事项。
3. 信息架构、用户流程和状态转换。
4. 功能需求，包含触发条件、输入、处理、输出和业务规则。
5. 权限、关键数据、外部依赖、异常与边界。
6. 页面及交互需求，涵盖加载、空、错误、权限和成功状态。
7. 验收标准及对应测试方式。
8. 埋点与运营观察计划。
9. 非功能要求、发布约束、兼容与回滚要求。
10. 待澄清问题、决策记录、变更历史。

PRD 的“已确认”仅针对一个版本。Agent 完整性检查是辅助，不替代负责人判断。

### 6.5 UI 设计、查看与切图

#### 6.5.1 设计生成规则

UI 的正式产物由结构化设计文档、样式规则、图片/矢量素材和渲染预览共同组成。整张生成图片可以作为参考，但不能单独标记为“开发就绪”。

生成步骤：选择 PRD 版本与目标平台 → 提取页面/状态/交互 → 选择视觉方向和约束 → 创建结构节点 → 生成独立素材 → 装配预览 → 检查 → 确认设计版本。

图片模型用于插画、照片、纹理等；文字、按钮、输入框、容器等优先以可描述的节点表达。素材透明背景、独立性和实际像素尺寸必须检查，不能仅依赖生成提示词。

| ID | 需求 | 规则与验收 | 范围 |
|---|---|---|---|
| UI-01 | 从 PRD 创建设计 | 选择需求/页面，继承文案、流程与约束；新增未在 PRD 中的功能标为提议 | 闭环首版 |
| UI-02 | 页面与状态树 | 页面关联需求；支持默认、加载、空、错误等必要状态，未覆盖状态显式提示 | 闭环首版 |
| UI-03 | 自研查看画布 | 缩放、平移、页面切换、选择模块、查看边界和节点属性 | 闭环首版 |
| UI-04 | 结构节点 | 至少包含页面、容器、文字、图片、矢量、基础形状；稳定 ID 和层级关系 | 闭环首版 |
| UI-05 | 布局语义 | 保存顺序、间距、内边距、对齐、固定/自适应尺寸及必要断点约束 | 闭环首版 |
| UI-06 | 样式与组件 | 统一颜色/字号/圆角等规则；可复用基础组件，允许关联项目已有组件名称 | 闭环首版 |
| UI-07 | 局部调整 | 支持改文案、颜色、间距、替换素材和指定区域重新生成；未选区域保持不变 | 闭环首版 |
| UI-08 | 素材管理 | 素材 ID、版本、文件类型、尺寸、来源与使用节点；同素材复用不重复生成 | 闭环首版 |
| UI-09 | 切图导出 | 指定节点或素材导出；PNG 与适用的 SVG；图片支持倍率选择但不虚称增加原始细节 | 闭环首版 |
| UI-10 | 交互说明 | 点击、跳转、禁用条件、反馈与状态转换可读；首版无需完整交互原型播放器 | 闭环首版 |
| UI-11 | 版本快照 | 固定版本的设计链接；后续修改不改变历史交付包的内容 | 闭环首版 |
| UI-12 | 复杂设计能力 | 复杂组件变体、动画、多断点可视编辑、设计系统库、实时多人协作 | 增强 |

#### 6.5.2 切图边界与格式

- 导出整卡片或整页面时，结果是预览/复合节点导出，需区别于“独立素材”。
- 独立主图不得混入卡片标题或按钮；透明插画不得包含伪透明棋盘格。
- 位图转成 SVG 包装不等于矢量化，格式信息应如实标注。
- 导出包包含素材清单、稳定 ID、推荐文件名、像素尺寸、倍率、校验值和节点引用。
- 同名不同版本文件不得静默覆盖；资源不可用时交付包进入不完整状态。
- 对于用户上传或导入素材，记录可取得的来源/许可说明；未知状态明确显示。

#### 6.5.3 设计交付验收

用户仅分享一个已授权的设计版本链接，Coding Agent 就能获得页面截图、模块结构、文字、布局、交互说明和可下载素材；不要求用户额外截图、量尺寸或整理文件。

### 6.6 开发交付包

| ID | 需求 | 规则与验收 | 范围 |
|---|---|---|---|
| HAND-01 | 生成不可变交付包 | 绑定 PRD、需求、UI、素材和仓库基准版本；具有包 ID 与内容校验值 | 闭环首版 |
| HAND-02 | 任务拆分 | 按可验收结果拆为任务，注明依赖、影响范围、不做事项及验收标准 | 闭环首版 |
| HAND-03 | 仓库约束 | 记录技术栈、目录、运行/测试方式、项目规则文件引用、已有组件与禁止修改范围 | 闭环首版 |
| HAND-04 | 上下文选择 | 任务级最小完整上下文；索引和分页支持按需读取，截断必须显式提示 | 闭环首版 |
| HAND-05 | 就绪检查 | 无权限、素材缺失、需求未确认或版本不一致时列出阻塞项；不生成假完整包 | 闭环首版 |

| ID | 需求 | 规则与验收 | 范围 |
|---|---|---|---|
| CODE-01 | 手动或 Agent 执行 | 同一个任务允许人工实现、外部 Agent 拉取或平台调度，不因执行方式改变验收标准 | 闭环首版 |

| CODE-03 | 任务领取与锁定 | 领取带租约与任务版本；默认一个执行者，避免两个 Agent 同时覆盖同一任务 | 闭环首版 |

平台收到完成回调后应验证任务 ID、执行 ID、所用基线版本和产物引用。无法核验的结果显示“待核验”，不得伪造通过状态。

| OPS-04 | 事件规划 | 在 PRD 阶段定义事件、属性、触发条件，编码/测试检查是否落实 | 闭环首版 |

## 7. 贯穿全流程的项目资产与追溯

### 7.1 核心对象

| 对象 | 关键字段/关系 |
|---|---|
| Workspace / Project | 成员、角色、项目策略、模型/执行配置、数据连接 |
| Iteration | 目标、范围、负责人、计划、当前基线、发布与复盘 |
| ProjectBrief / Decision | 项目假设、立项结论、原因、证据、确认人 |
| ResearchSource / Finding | 来源地址/附件、时间、片段、结论类型与置信说明 |
| Requirement | 稳定 ID、价值、来源、范围、优先级、验收标准、依赖 |
| PRDVersion | 文档结构、需求引用、问题、评审状态、版本 |
| DesignVersion / DesignNode | 页面/状态、层级、布局、样式、交互、关联需求 |
| AssetVersion | 类型、尺寸、来源、存储引用、校验值、使用节点 |
| HandoffBundle | 固定版本清单、任务上下文、素材索引、约束、校验值 |
| Task / AgentRun | 执行者、租约、依赖、状态、输入基线、进度、结果与成本 |
| CodeArtifact | 仓库、分支、commit/PR/补丁引用、作者与关联任务 |
| TestCase / TestRun / Defect | 验收引用、执行环境、提交、证据、严重度、复测 |
| Release | 候选构建、环境、授权、部署与检查、回滚引用 |
| MetricDefinition / Observation | 指标口径、来源、时间范围、版本、实际/估算标识 |
| Feedback / Operation / Review | 来源、行动、对外执行结果、复盘与后续需求 |

每种资产至少具备 ID、所属项目、创建/修改人、创建/修改时间、版本、状态及访问权限。附件/截图也必须关联资产，不能仅作为聊天中的临时链接存在。

### 7.2 追溯关系

证据 → 需求 → PRD 章节 → UI 页面/状态 → 开发任务 → 代码提交 → 测试用例与结果 → 发布 → 指标/反馈 → 新需求。

关系允许一对多、多对一，也允许无 UI 的需求直接关联实现。系统应回答：

- 这张页面对应哪些需求？
- 这次发布实现了哪些范围，哪些没有实现？
- 某需求是否有有效测试结论？
- 修改某条规则会影响哪些产物？
- 某运营反馈来自哪个版本，是否已经修复？

### 7.3 变更传播

1. 编辑创建新草稿版本，已确认版本保持不变。
2. 确认新版本后，计算显式关联的影响范围。
3. 后续产物标记“可能受影响／待复核”，说明变更位置。
4. 责任人选择无需修改并说明理由、局部更新或重新执行。
5. 正在运行的 Agent 收到变更事件；默认继续旧基线或暂停等待策略决定，不静默混用新旧输入。
6. 更新完成后生成新交付包和验证记录，保留历史链路。

自动影响分析首先依赖已建立的关联，模型补充建议单独标记，不承诺穷尽所有代码影响。

## 8. Agent、MCP 与 Skill 接入需求

### 8.1 两种方向必须分开实现

**外部 Agent 访问平台。** 平台作为 MCP 服务端，外部 Agent 经授权读取任务、PRD、设计、素材并回写结果。这是第一版优先实现的第三方接入路径。

**平台驱动外部 Agent。** 平台通过供应商允许的 API、SDK、CLI 或本地桥接适配器启动/取消执行、读取状态。它是额外执行能力，不由 MCP 服务端自动提供。适配器未提供的能力，界面应禁用或给出手工流程。

### 8.2 MCP 功能契约草案

以下是产品级工具分组与候选名称，最终协议 schema 在架构阶段确定。工具应具有明确输入输出、版本信息、权限语义、分页和结构化错误。

| 工具分组 | 候选工具 | 输出或作用 |
|---|---|---|
| 项目定位 | projects.list / projects.get | 可访问项目与基本约束 |
| 需求读取 | requirements.list / requirements.get | 需求、来源、验收与依赖 |
| 文档读取 | prd.get / artifacts.get | 指定版本和章节内容、附件资源 |
| 设计创建 | designs.create / jobs.get | 提交设计生成任务，查询异步结果 |
| 设计交付 | designs.get_context / designs.get_preview | 节点、布局、样式、交互和截图 |
| 素材交付 | assets.list / assets.export | 素材元数据及经授权的下载资源 |
| 任务协作 | tasks.list / tasks.claim / tasks.get_context | 可领取任务、租约、固定版本交付包 |
| 进度与澄清 | tasks.report_progress / tasks.request_input | 真实进度、问题和等待状态 |
| 结果提交 | tasks.submit_result | 提交代码和测试引用，进入待评审 |
| 测试回写 | tests.submit_result / defects.create | 带环境、提交和证据的验证结果 |
| 变更建议 | changes.propose | 提出 PRD/UI/范围修改，不直接覆盖已确认资产 |

第一版不开放任意 shell 执行作为通用平台工具，也不将秘密凭证放进任务上下文。发布/对外运营等动作需要专门权限和确认策略，不能伪装成普通结果提交。

### 8.3 工具协议要求

- 输入明确 project_id、对象 ID 与 version；写操作声明预期版本。
- 列表支持游标分页；上下文超限返回摘要、完整资源索引和截断提示。
- 图片预览和素材以客户端可消费的受控资源返回，下载地址可刷新，历史资产 ID 不变。
- 长任务立即返回 job_id，区分排队、运行、等待、失败和结果就绪。
- 写请求具有幂等标识；网络重试不能重复创建任务、上传结果或执行发布。
- 任务领取校验租约；过期执行者回写不能覆盖新执行者结果。
- 错误区分无权限、版本冲突、素材缺失、输入不完整、供应商不可用、预算限制和暂时故障。
- 凭证撤销后禁止继续访问；已经下载到外部环境的副本无法远程保证删除，分享说明应明确边界。

### 8.4 Skill 交付

Skill 是工作指南，不承担权限控制。即使未安装 Skill，MCP 工具也应可被理解和调用；安装后提高流程一致性。

建议第一版提供一个总入口和两个专用工作流：

1. **项目工作台入口**：解析项目/任务链接，确认版本，定位所需阶段与资源。
2. **按设计编码**：读取任务和项目规则 → 查看 PRD 与截图 → 下载素材 → 实现 → 运行必要检查 → 提交证据。
3. **测试与回写**：读取验收标准和执行环境 → 执行或明确无法执行 → 记录结果与缺陷 → 提交证据。

后续扩展调研整理、PRD 撰写、UI 生成和运营复盘工作流。Skill 应明确不把网页、文档、仓库评论中的不可信指令当作新的授权。

### 8.5 兼容性验收

第一版至少以两个独立的外部 Agent 客户端验证同一交付契约，其中优先包含 Codex；第二个客户端按实际可用接入能力选择。两者都应能读取同一份上下文、取得素材并提交可核验结果。未实测的客户端只标记“协议兼容待验证”，不宣称全面支持。

### 8.6 阶段执行与流程编排

各阶段均可选择人工操作或 Agent 辅助，不要求每个业务角色都部署一个独立 Agent。首版采用固定阶段模板与明确的阶段动作；可视化任意流程编排、多 Agent 自主协商属于后续增强。

| ID | 需求 | 规则与验收 | 范围 |
|---|---|---|---|
| FLOW-01 | 阶段动作模板 | 提供整理立项、归纳证据、起草 PRD、生成 UI、拆分开发任务、起草用例和复盘等动作；各有输入要求与产物类型 | 闭环首版 |
| FLOW-02 | 执行前说明 | 展示将使用的资产版本、执行者、预计产物、是否涉及外部调用及可取得的费用估算 | 闭环首版 |
| FLOW-03 | 人工接管 | Agent 失败或等待输入时，用户可直接编辑资产、补录结果或更换执行者；保留原运行记录 | 闭环首版 |
| FLOW-04 | 阶段续接 | 用户点击下一步时检查输入和策略，创建后续任务；不得仅根据上一阶段返回文本就自动确认成果 | 闭环首版 |
| FLOW-05 | 全局运行控制 | 项目内可查看所有运行，限制并发、取消排队、停止后续自动步骤，区分请求停止与实际停止 | 闭环首版 |
| FLOW-06 | 自定义工作流 | 支持阶段增减、条件分支、事件触发与不同 Agent 的依赖调度；执行图可审计 | 增强 |

当用户选择“连续执行至下一个确认点”时，系统可以完成已授权的草稿步骤，并在缺失必要输入、权限、预算或到达确认点时暂停。继续执行不得通过默认选择代替用户确认。用户主动选择的跳过阶段需记录原因和未产生的资产，不伪造阶段完成。

## 9. 权限、授权与执行策略

### 9.1 操作分类

| 类型 | 示例 | 默认策略 |
|---|---|---|
| 读取 | 查看需求、设计、任务 | 在项目权限内直接执行 |
| 草稿修改 | PRD 局部草稿、设计提议、用例起草 | 可撤销；记录变更；受版本校验约束 |
| 基线确认 | 确认范围、设计交付包 | 负责人或项目预授权策略决定 |
| 代码写入 | 改任务工作区、创建提交/PR | 必须有代码执行授权并限定仓库/范围 |
| 环境变更 | 安装依赖、修改配置、部署 | 按本地/测试/生产环境分别配置策略 |
| 外部影响 | 发布上线、发送消息、付费操作 | 需要明确授权或具体预授权，不从生成内容推断 |

### 9.2 必需能力

- 人与 Agent 分别审计，保留代谁执行、执行策略、输入版本和结果。
- 项目数据隔离；资源下载、预览缓存和导出任务都执行相同权限检查。
- 模型和执行凭证由受控配置引用，不写入文档、导出包或普通日志。
- 支持连接测试、权限查看、凭证轮换与撤销。
- 外发给模型/第三方 Agent 的数据范围应可配置，并提示实际接收方。
- 本地桥接只访问用户明确授权目录；取消任务不删除已有代码或用户文件。
- 上传文件限制类型和大小；不因导入文档自动执行其中脚本或命令。
- 高影响操作在执行前重新检查权限及目标状态，旧批准不能套用到已变化的发布内容。

## 10. 异常、恢复与一致性

| 异常 | 用户可见行为 | 系统规则 |
|---|---|---|
| 模型生成失败 | 显示失败阶段、已保留内容和重试入口 | 已完成产物不丢失，重试创建新 attempt |
| 图片素材未齐 | 页面可显示占位并标记未完成 | 不允许标成开发就绪；成功素材可复用 |
| 外部 Agent 断线 | 显示失联与最后心跳 | 先核实远端状态，避免重复启动同一写任务 |
| 重复回调 | 用户只看到一次有效提交 | 按事件/请求 ID 去重 |
| 版本冲突 | 提示变化位置并允许合并/重新提交 | 禁止旧版本静默覆盖 |
| 上游需求变更 | 下游产物显示受影响范围 | 新旧版本隔离，不自动重写代码 |
| 任务取消 | 显示取消请求与实际停止状态 | 远程已发生的副作用不能假装撤销 |
| 测试环境不可用 | 结果为受阻并列出原因 | 不记为通过，不混同业务缺陷 |
| 部署状态不确定 | 显示待核实，提供查询/人工确认 | 查询目标环境后再决定重试或回滚 |
| 指标数据缺失 | 展示缺失时间段与来源状态 | 不补造数据，不将缺失当作零 |
| 预算耗尽 | 暂停新的付费步骤，保留成果 | 已在途费用单列，估算限制不等于供应商硬限额 |
| 权限撤销 | 停止新的访问与动作 | 记录受影响运行，外部已发生动作单独处理 |

## 11. 通知、搜索与协作

### 11.1 通知

默认仅通知需要输入/授权、实质性失败、结果待评审、关键版本变化和发布结果。普通步骤进度保存在任务页，不逐条打扰用户。通知支持按任务去重、静默时段和项目级订阅。

### 11.2 搜索

可按项目、阶段、需求 ID、状态、负责人、版本搜索。结果展示来源对象和版本；不能把不同版本的互斥规则拼成一个无来源答案。基于项目资产的问答应提供可点击定位，超出证据的判断明确标记。

### 11.3 评论与待办

评论可锚定 PRD 段落、设计节点、需求和任务。待办有负责人、状态和截止日期；聊天中的承诺不会自动算完成。确认与决策记录不依赖评论是否被折叠或删除。

## 12. 外部系统与部署形态

### 12.1 集成边界

| 集成对象 | 平台读取/写入 | 第一版策略 |
|---|---|---|
| 模型与图片生成 | 提交受控任务、获取结果与用量 | 统一适配接口，先接一套可用供应商 |
| 第三方 Coding Agent | 上下文读取、任务领取、结果回写 | MCP 优先；主动调度按适配器能力开放 |
| Git 仓库 | 仓库元信息、提交/PR 引用、状态 | 先选一个平台；支持受控手工补录 |
| 测试/CI | 测试结果、构建产物、执行链接 | 标准结果导入与一个连接器即可 |
| 部署平台 | 目标环境、任务和实际部署结果 | 先支持手工登记与可核实证据 |
| 运营数据 | 反馈、事件指标、版本观察 | CSV/手工导入优先，实时连接器增强 |
| 通知渠道 | 工作区内通知，后续外部消息 | 默认站内；外部发送单独授权 |

### 12.2 部署需求

产品架构应允许 Web 工作台连接托管服务，也允许后续私有部署。首版只交付一种经过验证的服务端部署形态，避免双线维护；选型待用户确认。

本地桥接是可选执行组件：用于访问本地仓库、工具和设备。平台可以不上传完整代码仓库，改由本地执行后回传明确授权的摘要与产物。若用户选择外部 Agent 自主接手，可只使用平台 MCP 和现有 Agent 环境。

## 13. 非功能需求

### 13.1 性能与容量验收基线

以下是首版建议验收负载与目标，需在架构阶段确认测试环境；它们不是已达到的性能声明。

| 项目 | 建议验收条件 |
|---|---|
| 普通接口 | 在 20 个并发活跃会话测试下，常规列表/详情服务端 p95 小于 1 秒；外部服务等待不计入并单独展示 |
| 文档 | 5 万中文字符、200 个结构块的 PRD 可编辑；自动保存状态可见，失败可恢复 |
| 设计查看 | 单页面 500 节点，在约定桌面设备上选择/缩放交互 p95 小于 200ms；长任务异步 |
| 异步任务 | 创建请求应在 2 秒内受理并返回任务 ID；不承诺模型生成固定耗时 |
| 首版项目容量 | 验证 1,000 条需求、100 个页面版本索引、10,000 条任务/测试记录的分页与过滤 |
| 导出 | 大素材包后台生成，支持查询和重新下载，不占用页面同步请求 |

### 13.2 可靠性与恢复

- 已确认版本和交付包不可原地修改；还原会生成新版本。
- 数据库与素材存储有备份与恢复演练；建议首版以 RPO 不超过 24 小时、RTO 不超过 8 小时作为待确认目标。
- 草稿自动保存与断线恢复单独验证，不用灾备目标代替日常编辑保护。
- 任务状态转换可追溯，重复消息、进程重启和网络中断不能导致重复外部动作。
- 删除优先软删除和明确保留期；真正清理前检查历史版本与交付包引用。

### 13.3 可用性与无障碍

- 核心流程可用键盘完成；焦点状态清楚，状态不能只靠颜色表达。
- 设计画布提供可读模块树作为非视觉入口。
- 中文界面优先；文案、时间、时区与数字格式集中管理。
- 读写权限不足时提供说明，不出现可点击但必然无权限的主要动作。

### 13.4 可观测性与成本

- project_id、task_id、run_id、artifact_version 等关联到日志与事件。
- 记录外部调用时延、失败、重试、输入规模和可取得的用量，不保存不必要的敏感原文。
- 按项目设置运行并发、重试上限和预算提醒；没有可信费用数据时显示未知或估算。
- 对模型输出格式、任务完成率和素材可用性进行质量监测，不能只看调用是否返回 200。

## 14. 首版范围与演进路线

### 14.1 M0：最小完整闭环

目标：一个独立开发者或小团队完成一个小型 Web 项目迭代，从立项到发布后反馈回流。每个阶段可用，但集成和自动化深度受控。

**包括：**

- 单工作区、多项目、基础角色和单轮迭代范围管理。
- 可编辑立项卡、调研来源/结论、需求池和版本化 PRD。
- 独立 UI 节点文档、页面预览、必要状态、简单局部调整及素材导出。
- 固定版本交付包、MCP 和“按设计编码”Skill。
- 外部 Agent 领取/提交任务，支持人工介入和版本冲突提示。
- 手工用例与自动测试结果导入、缺陷复测、设计/实际截图并排对照。
- 发布检查、人工部署记录与证据核实。
- 反馈导入、基础指标口径与数据录入、复盘转需求。
- 权限、版本、异步任务、审计、预算显示和失败恢复的基础能力。

**首版不包括：**

- 完整专业矢量编辑、多端设计编辑器或复杂实时协作。
- 所有 Coding Agent 的主动启动与控制、多 Agent 自主并行集成。
- 多供应商 CI/CD、应用商店、广告和客服的全面适配。
- 自研完整 IDE、Git 托管、数据仓库、营销自动化或企业 ERP。
- 无人工介入自动完成立项到生产发布的承诺。

### 14.2 M1：自动化与团队协作深化

加入本地执行桥接、一个成熟 Coding Agent 调度适配器、CI/部署连接器、任务依赖调度、基础自动视觉对照、调研检索、运营数据连接器、团队评审策略和设计组件复用。

### 14.3 M2：多 Agent 与规模化

加入多仓库/多执行器协作、隔离工作区与冲突集成、复杂设计系统、移动端测试与分发、实验与留存分析、私有部署及企业治理。

### 14.4 建议建设顺序

1. 先建立对象 ID、版本、权限、异步任务和资产关系，避免后续各模块无法对接。
2. 打通立项—调研—需求—PRD，验证上游资产结构。
3. 实现 UI 文档、渲染、素材和交付包，验证设计可供编码使用。
4. 用外部 Agent 跑通领取、实现、提交、评审和测试，不先追求自动唤起所有 Agent。
5. 接通发布记录、反馈、指标和下一轮需求，完成全流程验收。
6. 根据试点的真实瓶颈增加连接器与自动化，避免先建设无人使用的复杂编排。

不在团队规模、技术条件、供应商和首版范围尚未确认前承诺具体周数。

## 15. 端到端验收场景

### E2E-01：从想法到运营回流

1. 创建“旅行目的地发现与收藏”项目，填写目标用户、目标指标与不做事项。
2. 收录调研材料，建立结论与证据引用。
3. 创建搜索、分类浏览、收藏需求并形成迭代范围。
4. 生成和人工修改 PRD，包含未登录、空列表、请求失败和重复收藏规则。
5. 创建发现页、详情页、收藏页及必要状态，导出独立照片与图标。
6. 确认交付包，由外部 Coding Agent 读取并实现。
7. Agent 返回可审查代码引用与测试证据；评审通过。
8. 按验收标准执行测试，记录并修复至少一个缺陷后复测。
9. 创建发布记录，核实目标环境版本和关键流程。
10. 导入一条反馈和一组版本观察数据，复盘后创建下一轮需求。

**通过标准：** 每一步产物均有 ID、版本与来源关系；从反馈能追溯到发布、测试、代码、设计和需求；没有把未执行的检查标为通过。

### E2E-02：外部 Coding Agent 直接使用设计

只给外部 Agent 一个授权任务链接。Agent 能定位固定版本 PRD/UI、取得独立素材、读取项目规则、实现并提交结果。不得要求用户另外发送截图、素材压缩包或手工复述布局。

### E2E-03：版本变化不污染在途任务

Agent 正在使用交付包 v1 时，用户将 PRD 改为 v2。平台生成影响清单并通知执行者；v1 资源仍可访问，结果明确绑定 v1；不能自动把该结果算作 v2 需求已完成。

### E2E-04：接入不具备主动调度能力的客户端

第三方 Agent 能访问 MCP，但不能被平台启动。平台展示“复制任务链接/由外部接手”，不显示伪造的启动成功。用户接手后仍能完成任务领取与结果回写。

### E2E-05：失败与重试

图片生成部分失败、结果回调重复、浏览器关闭后重开、Agent 断线分别测试。已成功资产保留，重复结果只入库一次，未知执行状态先核实，用户可恢复或取消。

### E2E-06：权限边界

项目 A 的 Agent 凭证不能访问项目 B 的文档、预览、素材下载和任务。凭证撤销后新请求失败；越权写入不改变资产状态并产生审计记录。

### E2E-07：测试证据有效性

旧 commit 的测试通过结果不能无条件用于新 commit。跳过、受阻和只构建成功的情况不得显示为所有验收标准通过。

### E2E-08：已有项目导入

关联一个已有仓库，只导入现有 PRD，从新迭代开始。历史立项与调研显示未补录，不阻止合法工作；新产生的设计、实现和测试关系仍完整建立。

### E2E-09：运营真实性

未接入数据时显示暂无数据；导入的指标保留口径和时间。Agent 提出的原因标为假设，反馈转需求保留原文。生成运营公告不会自动向外发送。

## 16. 产品发布门槛

1. M0 覆盖的各阶段均能人工操作完成，不依赖模型调用才能查看或编辑已有资产。
2. E2E-01 至 E2E-09 全部通过，已知限制明确记录。
3. 至少两个外部 Agent 客户端完成上下文与结果回写兼容性验证。
4. UI 素材导出经人工检查与文件检查，图片不混入无关 UI，格式与元信息一致。
5. 权限、版本冲突、幂等、异步恢复、备份恢复的关键验证完成。
6. 发布范围内不存在未解决的阻塞缺陷；其他已知问题有责任人和明确影响说明。
7. 首次体验能够从项目创建到任务交付，不需要开发人员改数据库或手工拼接内部对象 ID。
8. 未实现的自动化入口标为未开放，不用模拟状态冒充真实执行。

## 17. 主要风险与产品应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 全流程范围过大 | 每个模块都浅，闭环交付延后 | M0 保留所有阶段的基本能力，限制连接器和自动化深度 |
| 整图难以恢复设计结构 | UI 看起来完整但无法切图和开发 | 结构与素材共同生成；整图只作参考或预览 |
| 文档质量不足 | Agent 凭空补充规则 | PRD 完整性检查、待澄清清单、版本确认 |
| 外部 Agent 能力不一致 | 连接成功但无法执行/回写 | 能力声明、协议与适配器分层、真实客户端验收 |
| 用户在多个工具修改 | 资产与实际代码脱节 | 固定基线、提交引用、外部变更检测与待复核状态 |
| 自动化错误被连续放大 | 错误需求进入生产和运营 | 阶段证据、关键确认、分环境策略与回滚 |
| 模型成本与生成时延 | 用户难以控制投入 | 分步执行、局部重生成、预算/用量显示、复用已有资产 |
| 运营数据不足 | 生成没有依据的建议 | 缺失显式展示，先定义指标再收集数据，推断单列 |
| 团队采用成本高 | 需要迁移所有工具才能使用 | 支持已有项目导入、链接交付、阶段性接入 |

## 18. 待确认事项与后续交付

### 18.1 影响首版架构的待确认项

| 问题 | 当前默认 | 确认时机 |
|---|---|---|
| 平台是自用工具还是对外商业化 | 先验证可复用产品闭环，商业化计费后置 | 账户/部署设计前 |
| 服务端首发托管还是私有部署 | 尚未确定，只交付一种首发形态 | 架构设计前 |
| 首个被构建的项目类型 | 小型 Web 项目 | 首版验收样例确定时 |
| 第一批第三方 Agent | 优先 Codex，第二客户端待核实选择 | 接入验证前 |
| 代码与 CI 平台 | 尚未指定 | 连接器开发前 |
| 图片/文本模型及凭证模式 | 使用可替换适配层，供应商未指定 | 成本评估与生成验证前 |
| Agent 是否需主动调度本地工具 | 首版优先外部拉取，主动调度增强 | 首版范围确认时 |
| 商业化、成员数量、保留期和合规要求 | 未定义 | 对外上线前 |

### 18.2 下一步建议产物

本需求文档确认后，按顺序完成：页面与关键交互原型 → 核心对象/版本/权限架构 → MCP 与交付包协议 → 首版任务拆分与验收计划 → 开发。先验证“一个完整迭代”与“设计链接被 Agent 直接使用”，再扩大自动化范围。

### 18.3 文档维护规则

新增或修改需求保留 ID；范围变化更新本文件版本和相应验收场景。功能落地后以可验证实现、测试与运行记录更新状态，不根据计划或 Agent 自述标记完成。
